# 딜 계산기 (상금 분배)

상태: 완료

## 목적 (한 줄)
토너먼트 종료 전 딜(칩 촙)을 할 때, 보유 칩 기준으로 상금을 어떻게 나눌지 현장에서 즉시 계산한다.

## 사용자 시나리오
1. 토너먼트 중 4명 남은 상황에서 "그냥 나눠먹자"는 얘기가 나온다.
2. 홈 화면에서 `딜 계산기` 카드를 눌러 진입한다.
3. 두 가지 모드 중 하나를 고른다.
   - **간편 모드**: 총 상금 하나만 있을 때
   - **정밀 모드**: 등수별 상금(1등/2등/3등…)이 정해져 있을 때
4. 상금은 기본값이 이미 채워져 있으므로, 대개 각자 보유 칩만 입력하면 된다.
5. 계산 결과가 즉시 표에 나온다. 만원 단위로 떨어지므로 현금을 바로 나눌 수 있다.
6. 계산이 끝나면 페이지를 닫는다. 저장하지 않는다.

## 요구사항

### R0. 상금 입력 단위 (확정)
- **상금 입력은 "만원" 단위, 정수만 입력한다.** (`40` = 400,000원)
- 내부 계산과 결과 출력은 모두 **원 단위**로 수행한다. (입력값 × 10,000)
- 상금 입력란에는 콤마 자동 표기를 적용하지 않고, 필드 우측에 `만원` 라벨을 붙인다.
- **보유 칩 입력은 이 규칙과 무관하다.** 칩은 정수 + 1,000 단위 콤마 자동 표기.
- 단위 변환은 입력/출력 경계의 단일 상수 `PRIZE_UNIT = 10000` 으로만 처리한다.
  (계산 로직 내부에는 10000이라는 숫자가 흩어져 있지 않아야 한다)
- 이 규칙의 결과로 **총 상금은 항상 10,000의 배수**임이 보장된다. R6은 이 전제에 의존한다.

### R1. 페이지 구성
- 신규 단일 파일 `deal-calculator.html`
- 기존 `index.html`(정산 계산기)과 **코드/데이터 공유 없음**. 완전 독립 페이지.
- 상단에 `← 홈` 버튼 (`location.href = '/'`)
- 모바일 우선 레이아웃 (현장에서 폰으로 사용)

### R2. 모드 선택
화면 최상단에 2개 토글 버튼. 기본 선택은 **간편 모드**.

| 모드 | 라벨 | 입력 | 계산 |
|---|---|---|---|
| simple | 간편 (총 상금) | 총 상금 + 각자 칩 | 칩 비율 분배 |
| icm | 정밀 (등수별 상금) | 등수별 상금 + 각자 칩 | ICM |

- 간편 모드 화면에 안내 문구 고정 노출:
  `등수별 상금 차이가 있다면 '정밀' 모드를 쓰세요. 칩 비율만으로 나누면 칩 리더가 과하게 가져갑니다.`
- 모드를 전환해도 이미 입력한 **칩 값과 이름은 유지**한다. (상금 입력란만 교체)
- 두 모드의 상금 입력값은 **서로 독립적으로 보관**한다. 모드를 왕복해도 각자 값이 유지된다.

### R3. 인원 설정
- 인원수 선택: **2 ~ 9명**. 기본값 4명.
- 인원수 변경 시 플레이어 행과 (정밀 모드의) 상금 행이 즉시 증감한다.
- 인원을 줄일 때는 뒤쪽 행부터 제거한다.

### R4. 입력 필드 및 기본값

| 필드 | 기본값 | 비고 |
|---|---|---|
| 이름 | 비어 있음 | 선택 입력. 비면 `P1`, `P2`… 로 표시 |
| 보유 칩 | 비어 있음 | 필수. 0보다 큰 정수, 콤마 자동 표기 |
| 총 상금 (간편) | **70** | 만원 단위 = ₩700,000 |
| 1등 상금 (정밀) | **40** | 만원 단위 = ₩400,000 |
| 2등 상금 (정밀) | **20** | 만원 단위 = ₩200,000 |
| 3등 상금 (정밀) | **10** | 만원 단위 = ₩100,000 |
| 4등 이하 (정밀) | **0** | 인원수만큼 행 생성, 기본 0 |

기본값 적용 규칙:
- 기본값은 **페이지 최초 로드 시 1회만** 채운다. 사용자가 수정하거나 비운 값을
  자동으로 되돌리지 않는다.
- 인원수를 늘려 **새로 생기는 등수 행**의 기본값은 0이다.
  단, 최초 로드 시 인원이 3명 이하여서 1~3등 행 중 일부가 없었다가 이후 인원을 늘린
  경우에는, 해당 등수 행이 처음 생성되는 시점에 위 표의 기본값(40/20/10)을 채운다.
- 인원수를 줄였다가 다시 늘리면, 줄이기 전 입력값을 복원하지 않고 위 규칙을 따른다.
- 간편 모드의 총 상금 기본값 `70`은 **인원수와 무관하게 고정**이다.
  (정밀 모드 기본값 합계와 4명 기준으로 일치하지만, 인원이 바뀌어도 연동하지 않는다)

기타 입력 규칙:
- 등수별 상금은 **0 또는 빈칸 허용**. 빈칸은 0으로 처리한다.
  (4명 남았는데 3등까지만 지급하는 상황이 흔함)
- 정밀 모드는 상금 합계를 실시간으로 표시한다. 이 합계가 곧 총 상금.
  표시는 만원과 원을 함께 노출한다. 예: `합계 70만원 (₩700,000)`
- 등수별 상금이 내림차순이 아니어도 계산은 수행하되,
  `2등 상금이 1등보다 큽니다` 형태의 경고를 표시한다. (차단은 하지 않음)

### R5. 계산 로직

#### R5-1. 간편 모드

```
분배액(i) = 총 상금 × (칩(i) / 전체 칩 합계)
```

#### R5-2. 정밀 모드 — ICM (Malmuth-Harville)
1. 상금 배열(원 단위 변환 후)에서 **0이 아닌 마지막 등수의 인덱스 + 1**을 `k`로 둔다.
   (예: 4명 / 상금 `[40, 20, 10, 0]` → k = 3)
2. 1등부터 k등까지의 순열만 재귀 탐색한다. 나머지 등수는 상금이 0이므로 계산 불필요.
3. 재귀식:
   - 남은 플레이어 집합에서 다음 등수를 차지할 확률 = `칩(i) / 남은 칩 합계`
   - 해당 등수 상금 × 누적 확률을 `equity(i)`에 더한다
   - 그 플레이어를 제외하고 다음 등수로 재귀

```js
function icm(chips, prizes) {
  const n = chips.length;
  const equity = new Array(n).fill(0);
  let k = 0;
  for (let i = 0; i < prizes.length; i++) if (prizes[i] > 0) k = i + 1;
  if (k === 0) return equity;

  function recurse(remaining, remainingTotal, place, prob) {
    for (const i of remaining) {
      const p = prob * chips[i] / remainingTotal;
      equity[i] += p * prizes[place];
      if (place + 1 < k) {
        recurse(remaining.filter(x => x !== i), remainingTotal - chips[i], place + 1, p);
      }
    }
  }
  recurse([...chips.keys()], chips.reduce((a, b) => a + b, 0), 0, 1);
  return equity;
}
```

- 연산량은 최대 `9 × 8 × ... × (9-k+1)`. 9명 전원 지급이어도 362,880회로 즉시 끝난다.
  별도 최적화나 라이브러리 없이 위 재귀 그대로 사용한다.

### R6. 반올림 — 최대잔여법 (만원 단위)

**목표: 모든 분배액이 10,000원의 배수이면서, 합계가 총 상금과 1원의 오차도 없이 일치할 것.**

R0에 의해 총 상금은 항상 10,000의 배수이므로, 아래 절차는 항상 정확히 떨어진다.

1. 총 배분 단위 수 `U = 총 상금 / 10,000` 을 구한다. (정수)
2. 각자 원값을 10,000으로 나눈 뒤 **내림**하여 단위 수 `u(i)` 를 구한다.
   나머지 `r(i) = 원값 − u(i) × 10,000` 을 함께 보관한다.
3. `남은 단위 = U − Σu(i)` 를 계산한다. (0 이상, 플레이어 수 미만)
4. `r(i)` 가 **큰 사람부터** 1단위씩 배분한다. 남은 단위가 0이 되면 중단.
5. 동점 처리: `r(i)` 가 같으면 **보유 칩이 많은 사람** 우선.
   칩도 같으면 **입력 순서**가 빠른 사람 우선.
6. 최종 분배액 = `u(i) × 10,000`

부동소수점 주의:
- `r(i)` 비교 시 부동소수점 오차로 순서가 뒤집힐 수 있다.
  내림 계산은 `Math.floor(원값 / 10000)` 로 수행하고,
  합계 검증은 **단위 수(정수)** 기준으로 하여 원 단위 실수 비교를 피할 것.

### R7. 결과 표시
표 형태로 아래 열을 노출한다.

| 열 | 내용 |
|---|---|
| 플레이어 | 이름 (또는 P1…) |
| 보유 칩 | 콤마 표기 |
| 칩 비율 | 소수점 1자리 % |
| 분배액 | 만원 단위 최종 금액 (강조 표시) |

- 분배액은 **만 단위를 크게, 원 단위를 보조로** 표기한다. 예: `38만 (₩380,000)`
  (R6에 의해 만 단위 값은 항상 정수이므로 소수점이 표시되면 안 된다)
- 표 하단에 `합계` 행을 두고, 총 상금과 일치함을 보여준다.
- **정밀 모드일 때만** 참고 열 `칩 비율 분배` 를 함께 노출한다.
  (ICM 결과와 나란히 비교 → 왜 다른지 즉시 납득 가능)
- 입력이 바뀌면 버튼 없이 **실시간 재계산**한다.

### R7-1. 0원 발생 시 안내
만원 단위로 끊으면서 분배액이 **0원이 되는 플레이어**가 생길 수 있다.
(ICM 지분이 10,000원 미만이고 잔여 단위 배분에서도 밀린 경우)

- 계산 자체는 그대로 둔다. 강제로 최소 1만원을 주지 않는다.
  (총 상금 정합성이 깨지므로)
- 대신 결과 표 하단에 안내를 노출한다:
  `{이름}님의 지분이 1만원 미만이라 0원으로 계산됐어요. 만원 단위로 나누는 특성상 발생할 수 있습니다.`

### R8. 검증 및 예외 처리
- 칩 합계가 0이면 결과 영역에 `보유 칩을 입력해주세요` 표시, 계산 중단.
- 총 상금(또는 상금 합계)이 0이면 `상금을 입력해주세요` 표시, 계산 중단.
- 칩에 0 또는 음수 입력 시 해당 입력란을 빨간 테두리로 표시하고 계산 중단.
- 숫자 외 문자는 입력 단계에서 제거한다.

### R9. 홈 진입점
`index.html`의 `HOME_ENTRIES` 배열에 항목 1개 추가.

```js
{
  id: 'deal', title: '딜 계산기', desc: '보유 칩 기준 상금 분배',
  href: '/deal-calculator.html', color: '미정 - 확인 필요', category: null,
  icon: '미정 - 확인 필요'
}
```

- 색상/아이콘 미정. 기존 카드와 겹치지 않는 팔레트 색상 하나와 단순 도형 SVG를
  선택해 진행하고, 구현 보고 시 어떤 값을 썼는지 명시할 것.
  (이 항목은 구현을 막지 않는다)

## 완료 조건 (Claude Code가 스스로 검증할 기준)

### C0. 기본값
- 페이지 최초 로드 시 인원 4명, 간편 모드, 총 상금 `70`이 채워져 있을 것.
- 정밀 모드로 전환하면 `40 / 20 / 10 / 0`이 채워져 있고, 합계가 `70만원 (₩700,000)`으로 표시될 것.
- 상금 값을 수정한 뒤 모드를 왕복해도 수정값이 유지될 것.

### C1. 테스트 벡터 — 정밀 모드(ICM)
입력: 칩 `[5000, 3000, 1500, 500]`, 상금 `[50, 30, 20, 0]` (= 원 단위 `[500000, 300000, 200000, 0]`)

**1단계** — 반올림 전 ICM 원값이 아래와 ±1원 이내로 일치할 것:

| 플레이어 | 칩 | ICM 원값 |
|---|---|---|
| P1 | 5,000 | 377,780.66 |
| P2 | 3,000 | 312,888.64 |
| P3 | 1,500 | 225,602.45 |
| P4 | 500 | 83,728.04 |

**2단계** — R6 적용 과정이 아래와 같을 것:

| | 내림 단위 | 나머지 |
|---|---|---|
| P1 | 37 | 7,780.66 |
| P2 | 31 | 2,888.64 |
| P3 | 22 | 5,602.45 |
| P4 | 8 | 3,728.04 |

- 단위 합계 98, 총 단위 100 → 남은 단위 2개
- 나머지 상위 2명(P1, P3)이 1단위씩 추가 획득

**3단계** — 최종 결과가 정확히 아래와 같을 것:
`P1 380,000 / P2 310,000 / P3 230,000 / P4 80,000` (합계 1,000,000)

### C2. 테스트 벡터 — 간편 모드
입력: 칩 `[5000, 3000, 1500, 500]`, 총 상금 `100` (= ₩1,000,000)
결과: `500,000 / 300,000 / 150,000 / 50,000` (합계 1,000,000)
→ 원값이 이미 만원 단위로 떨어지므로 잔여 배분이 발생하지 않아야 한다.

### C3. 두 모드 일치 검증 (핵심)
정밀 모드에 상금 `[100, 0, 0, 0]`(우승자 독식)을 입력하면
간편 모드에 총 상금 `100`을 입력한 결과와 **완전히 동일**해야 한다.
→ 단일 상금일 때 ICM은 수학적으로 칩 비율과 같아지므로, 이게 어긋나면 ICM 구현이 틀린 것이다.

### C4. 합계 정합성 (최우선 검증 항목)
인원 2~9명, 칩 값과 상금 구조를 무작위로 바꿔 **최소 50회** 계산했을 때,
모든 경우에 아래 두 조건이 동시에 성립할 것:
1. **분배액 합계 = 총 상금** (1원의 오차도 없이)
2. **모든 분배액이 10,000의 배수**

칩 값에 극단적 편차(예: `[100000, 100, 100, 100]`)를 주는 케이스,
상금이 1등 몰빵인 케이스, 총 상금이 인원수로 나눠떨어지지 않는 케이스를 반드시 포함할 것.

### C5. 0원 케이스
분배액이 0원인 플레이어가 발생하는 입력을 하나 만들어,
R7-1의 안내 문구가 정상 노출되고 그 상태에서도 C4의 두 조건이 성립함을 확인할 것.

### C6. 예외 처리
R8의 4개 예외 케이스가 각각 의도대로 동작하고, 콘솔 에러가 발생하지 않을 것.

### C7. 독립성
`deal-calculator.html`이 Firebase SDK를 로드하지 않고, localStorage에 아무것도 쓰지 않을 것.

### C8. 진입
홈 화면에 `딜 계산기` 카드가 노출되고, 클릭 시 정상 진입할 것.

## 제외 범위 (이번에 안 하는 것)
- **천원/원 단위 정밀 분배** — 만원 단위로 확정. 현금 분배 편의를 우선함
- **분배 단위 토글(만원/천원 선택)** — v1 실사용 후 필요하면 재검토
- **0원 플레이어에 대한 최소 금액 보장** — 총 상금 정합성이 깨지므로 하지 않음. 안내만 노출
- **상금의 소수점/원 단위 세부 입력** — 만원 단위 정수만
- **Firestore 저장 / 계산 기록 보관** — 현장에서 즉시 확인하고 끝내는 용도
- **결과 이미지 공유(html2canvas)** — 화면을 직접 보므로 불필요
- **기존 정산 계산기(`index.html`)와의 연동** — 완전 별개 기능
- **"세이브 후 촙"(전원 최소 상금 확보 후 잔여분만 칩 비율 분배) 방식** — v1 실사용 후 재검토
- **블라인드 레벨/스택 깊이를 반영한 보정** — ICM의 한계이지만 v1 범위 밖
- **로그인/권한 처리** — 계산기는 누구나 사용 가능

## 참고 (관련 파일, 기존 코드, 디자인 톤)
- 진입점 등록: `index.html`의 `HOME_ENTRIES` 배열
- 디자인 톤: 기존 사이트 라이트 테마 및 한국어 UI 라벨 스타일 유지
  (`--gold`, `--felt`, `--bg-elev`, `--text-dim` 등 기존 CSS 변수 네이밍 관례 따를 것)
- 숫자 표기 관례: `index.html`의 `fmt()`(₩ + 콤마), `fmtKor()`(만 단위),
  `formatThousands()`(입력 중 콤마) 참고.
  **코드를 import 하지 말고 필요한 부분만 이 파일 안에 다시 작성한다.**
- ICM 참고: Malmuth-Harville 모델. 별도 라이브러리 사용 금지, 순수 JS 재귀로 구현.
